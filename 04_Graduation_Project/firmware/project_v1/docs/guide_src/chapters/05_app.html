Chapter 5Subsystems — the APP layer

Eight modules carry the behaviour: two user interfaces (UIREM, UILOC), the security core (SEC, ALARM) and four features (LIGHT, DOOR, CLIMATE, HEATER). Each is a non-blocking state machine: it keeps its state in static variables, runs to completion every time it is called, and never waits. The state tables follow the code, not the design documents.

5.1 SEC — sessions, roles and the lockdown counter APPN

Purpose

SEC decides who is logged in where, what role they have, and when the system locks. It keeps one session and one failure counter per login source: SEC_SOURCE_REMOTE (UART) and SEC_SOURCE_LOCAL (keypad).

SEC session machine (per source) and the lockdown transition.

Events and transitions

  • Login(src, name, pass) — one attempt = one name+password pair checked together; the reply never says which half was wrong.
    • If the alarm is active, the result is SEC_LOGIN_LOCKED and nothing is checked.
    • REMOTE: the admin record first (only for this source, SEC-01), then the remote list. LOCAL: the keypad list, and only if SEC_u8IsLocalAllowed().
    • On success: fail[src] = 0 and a role is set. An admin login also opens the USERDB write gate, sets local-allowed = 0 and ends any keypad session (decision 1). A keypad login posts EVQ_LOCAL_SESSION(1).
    • On failure: ++fail[src]; at 3 (SEC_MAX_FAILED_LOGINS) it calls ALARM_voidTrigger() and returns SEC_LOGIN_LOCKED (SEC-05: the 3rd failure, decision 2).
  • Logout(src) — ends the session. For the admin it closes the write gate and resets local-allowed; for the keypad it posts EVQ_LOCAL_SESSION(0).
  • SetLocalAllowed(x) — effective only while the admin is logged in; x = 0 also ends a keypad session (SEC-08).

SEC_u8IsLocalAllowed() = not locked AND NOT (remote role is ADMIN and local-allowed = 0). A successful login on the same source resets its counter, and the two counters are independent, so 2 wrong on the terminal + 2 wrong on the keypad does not lock (test T-11).

5.2 ALARM — latched lockdown APPN

ALARM: once active, only an MCU reset leaves the state.

ALARM_voidTrigger() brings the system to its safe state (decision 2): HEATER_voidForceOff() (both elements off, display blank, panel LOCKED), CLIMATE_voidForceOff() (fan off, FORCED_OFF), buzzer on, post EVQ_LOCKDOWN. Lamps, dimmer and door keep their state. The 500 ms task toggles the buzzer, 0.5 s on / 0.5 s off (ALARM_BUZZER_BEEP 1; 0 makes it continuous, D-15). The lockdown state is not stored in EEPROM, so a reset always clears it (SEC-05, ALM-01). Both UIs poll ALARM_u8IsActive() and switch to their own LOCKED state, which ignores all input.

Call order: ALARM calls HEATER and CLIMATE, and SEC calls ALARM, so the modules were built and tested bottom-up: LIGHT → DOOR → CLIMATE → HEATER → ALARM → SEC.

5.3 LIGHT — lamps and dimmer APPN

No modes, only data: a 5-bit lamp mask and the dimmer percentage; both start at 0 at boot (lamp and dimmer states are not stored, D-14).

  • LIGHT_u8ToggleLamp(n) (n = 1…5) flips the bit and calls LAMP_u8SetState. Only if the chip acknowledged does it post EVQ_LAMP(n); on an I²C error the bit is flipped back, so LIGHT, LAMP and the chip stay consistent.
  • LIGHT_voidSetDimmer(p) clamps p to 100, rounds down to a multiple of 10 (LIGHT_DIMMER_STEP), sets the PWM, and posts EVQ_DIMMER only if the value changed.

5.4 DOOR — servo door, admin only APPN

DOOR: two states; SetState returns whether the servo moved.

Closed = DOOR_CLOSED_ANGLE 0° (1.0 ms pulse), open = DOOR_OPEN_ANGLE 90° (1.5 ms). Only UIREM calls DOOR, and only for the admin (commands 7 and 8). Because nothing else can move the door, DOOR posts no event. Boot = closed (D-14).

5.5 CLIMATE — air conditioning with hysteresis APPN

Purpose

Keep the room between 21 and 28 °C with an on/off fan (AC-01, AC-02, AC-03).

CLIMATE state machine. Hysteresis: between 21 and 28 °C the fan keeps its state.

Algorithm

Every 100 ms: one ambient sample into a MAVG_t, in every state, so the UIs can always show the room temperature. In WAIT nothing is decided until 10 samples exist (1 s after boot). Then, in quarter degrees: AC_OFF → AC_ON when avg_x4 > 28 × 4 = 112 (strictly above 28 °C); AC_ON → AC_OFF when avg_x4 < 21 × 4 = 84. Each change sets the fan (CLIMATE_FAN_SPEED = 100 % or 0) and posts EVQ_AC. FORCED_OFF (lockdown) stays until reset. The 7-degree band prevents the fan from chattering around a single threshold.

Integration

CLIMATE_voidInit() after FAN and LM35; CLIMATE_voidTask100ms() in the 100 ms slot. CLIMATE_voidFeedSample is public so that test_app can inject temperatures. Getters: CLIMATE_u8IsAcOn, CLIMATE_u8IsTempValid (0 during the first second), CLIMATE_u8GetRoomTemp (rounded °C).

Measured in simavr: ambient 25 → 30 °C at t = 22 s; [INFO] AC is now ON completed {{ f(R['latency']['ambient_step_to_ac_info_ms'],0) }} ms later. The 7th sample after the step lifts the average above 28 °C: (7 × 30 + 3 × 25) / 10 = 28.5.

Control law (HTR-07 … HTR-09)

The water LM35 is sampled every 100 ms in every state, so the UIs can show the water temperature while the heater is off. Decisions are made only in RUN/SET and only when MAVG_u8IsFull: after turn-on the average restarts (decision 5), so the first decision comes after 10 samples, about 1 s (HTR-08). The outputs are refreshed by the 100 ms task and by the 500 ms task (which toggles the phase); HEATER_voidShow writes the display only when the shown number or the blank state changes, so a stable value costs no I²C traffic.

Two timing effects of this design (measured in simavr, see §7.5)
  • On turn-off the elements go off at once, but the display and the LED follow in the next 100 ms or 500 ms task, i.e. up to 100 ms later. architecture.md §5.6 describes all four as immediate.
  • After an Up/Down press the set value appears at the next 100 ms task. If that task falls 2 ms before a 500 ms phase toggle, the value is blanked again 2 ms later and reappears at the next "on" phase, up to 0.5 s later. The comment in HEATER_voidRestartSetting ("the value is visible at once") describes the intent; about one press in five hits this window.

Persistence (HTR-04, decision 6)

The working copy lives in HEATER; the stored copy is byte 0x10 of the ESTORE image. Saving happens when setting mode times out, on turn-off, and at once for a remote or keypad change — in each case only if the value differs from the stored byte, so an unchanged value costs no EEPROM write and no event. At boot an invalid stored byte (not 35…75 in steps of 5) gives 60; that 60 is written only at the next save (eeprom_map.md §4 says "stores it", which suggests at once).

Integration

HEATER_voidInit() after ESTORE, RELAY, LED, SEVEN_SEG, BUTTON and LM35. In the loop: HEATER_voidTask10ms() after BUTTON_voidUpdate() in the same slot, so a button event is handled in the pass that detects it; HEATER_voidTask100ms(); HEATER_voidTask500ms(). Getters for the UIs: HEATER_u8IsOn, HEATER_u8GetElement, HEATER_u8GetWaterTemp, HEATER_u8GetSetTemp.

5.7 UILOC — keypad and LCD APPN

Purpose

The local interface for keypad users (LUI-01 … 04): login with numeric ID and PIN, a menu for lamps, dimmer, AC and heater, and a status screen when nobody is using the keypad.

UILOC state machine. Keys: digits, = Enter, * or C back, +/- step (D-7).

How a pass works

UILOC_voidTask10ms always takes the key from KPAD first, so a key pressed while it means nothing is not kept for later. It then checks, in this order:

  1. LOCKED → return.
  2. Alarm active → LOCKED screen.
  3. MESSAGE → count down 2 s.
  4. Logged-in screen but SEC says role NONE (the admin logged in or blocked the keypad) → STATUS.
  5. ID/PIN being typed but the keypad is no longer allowed → "Keypad blocked". Without this check, SEC would refuse the login and count a failure.
  6. Otherwise the key goes to the state's handler.

Every handler only changes RAM and calls UILOC_voidDraw(), which rewrites the whole wanted screen in LCD_BUF. LCD_BUF then sends only the cells that changed, so a redraw neither blocks nor flickers. UILOC_voidTask1s refreshes the values every second, flips the status page every 3 s, and ends a session (or a half-typed login) after 30 s without a key.

5.8 UIREM — the UART terminal APPN

Purpose

The remote interface (RUI-01 … 04): banner and login, role-specific menus, 17 commands with an argument either on the same line or prompted, [OK]/[ERR] replies, and [INFO] lines for every change made elsewhere. The full command list is Appendix D.

UIREM input states. Output is decoupled through a print queue.

The output rule: never block on a 128-byte ring

The admin menu is 408 bytes; the TX ring holds 128. UIREM therefore never prints a reply in one go. Every reply is a chain of messages in a 6-entry print queue (for example error line → menu → prompt). Multi-line messages (menu, status block, user list) print one line per step.

The task does nothing while fewer than UIREM_TX_RESERVE = 64 bytes are free, and it reads typed input only when the queue is empty. The result: no output is ever dropped, the echo of a typed line always fits, and typed bytes simply wait in the RX ring. The cost per 5 ms call is bounded by one line of at most 64 bytes copied into the ring.

Events, mute and idle

  • An [INFO] event is printed only at the prompt and only when nothing has been typed yet (TERM_u8IsLineEmpty), so it never cuts into a half-typed line. It is followed by the prompt again.
  • While nobody is logged in, events are read and discarded. The lockdown alert is printed from ALARM_u8IsActive() whoever caused it, even with nobody logged in.
  • EVQ is muted around commands 1, 2, 5 and 16, whose result is answered with [OK]. It is not muted around login, logout and command 9, so the admin sees [INFO] Keypad user logged out when the admin's own action ended a keypad session.
  • 120 s without a received byte ends the session (D-11), so an admin who walks away does not block the keypad for ever.
Login and admin menu in the Proteus terminal. Command 6, system status.

Integration

UIREM_voidInit() last among the APP inits; it queues the banner. UIREM_voidTask5ms() in the 5 ms slot (after LCD_BUF_voidUpdate), UIREM_voidTask1s() in the 1 s slot. TERM must be initialised first, at boot step 2.
