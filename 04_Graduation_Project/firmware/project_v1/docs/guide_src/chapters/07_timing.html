Chapter 7System timing analysis

How long everything takes, how late anything can be, and how much margin is left. Every figure is either computed from F_CPU, the configuration constants and the data sheet, or measured in simavr on the unchanged application binary. Proteus observations recorded in the repository are quoted where they exist.

7.1 Method

Computed values

Clock-derived values (timer periods, baud rate, ADC and SCL timing) follow from the register settings of chapter 2. They are exact, apart from the crystal tolerance. Bus times are counted in SCL periods: one byte with its ACK = 9 periods = 90 µs; a START is counted as one period. CPU times of ISRs are counted in cycles from the disassembly of an avr-gcc 7.3.0 build made with the PlatformIO flags (-Os -flto -ffunction-sections -fdata-sections; this build has the same RAM layout as pio run).

simavr measurements

simavr 1.6 is a cycle-accurate AVR simulator. A harness (guide_src/sim/harness.c) loads app.elf and emulates every external part:

  • the four PCF8574 chips and a 24C08 with a 5 ms write cycle (the real chip; the Proteus model has none);
  • the keypad matrix, which follows the column the firmware drives low;
  • the three buttons, both LM35 inputs, and the terminal (bytes injected one frame time apart).

The harness steps the CPU one instruction at a time and logs, with cycle timestamps:

  • every served scheduler slot (from the SCHED_u8IsTaskDue call that returns 1 to the next call);
  • every ISR (vector entry to the end of reti);
  • every I²C transaction, the relay/LED/buzzer pins and all UART output.

Three faults in simavr's TWI and ADC models had to be fixed first (the patch is kept in guide_src/sim/):

  1. writing 1 to TWINT did not clear the flag;
  2. SLA+W returned status 0x28 instead of 0x18;
  3. writing 1 to ADIF set the flag instead of clearing it, so polled conversions returned stale data.

The TWI bit time was also tied to TWBR: v1.6 counts one SCL period as 1 µs, ten times too fast for 100 kHz.

Two scenarios were run:

  • main (30 s): first boot on a blank EEPROM, admin login, user management, 1 3, 2 70, 5 65, door, status, keypad login and lamp toggle, heater on, setting mode, water and ambient steps, logout, three wrong logins.
  • stress (16 s): back-to-back EEPROM writes while the keypad toggles lamps, the heater blinks in setting mode, and the terminal prints status blocks and user lists.
Limits simavr is not the hardware. Its I²C has ideal edges and no clock stretching; a START is modelled as one SCL period; external parts answer instantly. The cross-check validates the firmware's own timing — code paths, scheduling, bus traffic counted in bytes — against the computed model. The I²C byte durations agree with computation and with the Proteus figure in hal_summary.md (§7.3). A stuck bus was not simulated; its case is computed in §7.7.

The blink corner case seen in simavr: the press is shown by the 100 ms task, and the 500 ms task blanks it 2 ms later.

Why the corner case exists. HEATER_voidRestartSetting sets the blink phase to 1 but leaves the 500 ms flag on its own fixed grid. Every 5th 100 ms task (tick ≡ 501 mod 500) runs 2 ms before a 500 ms task. A press that is first shown by that task is blanked almost at once, and the new value is next seen at the following "on" phase, ≤ 500 ms later. HTR-11 still holds (blinking at a 1 s period; the value is never wrong), but "every change is shown immediately" is met only in about 4 of 5 presses. A fix would be to restart the blink timing at each press, for example by counting the phase in the 100 ms task instead of using the 500 ms flag.

Worst alignment (computed)

Because the tasks are released on different ticks, a slot can only be delayed by a slot released before it that has not finished. The tightest sequence is ticks 1001–1005 (mod 1000), using the computed bounds of §7.4:

The loop is busy from 1002.00 to 1004.78 ms, a 2.8 ms stretch, once per second at worst. No release is delayed by more than 1.15 ms, and no flag comes anywhere near being set a second time before it is served. The smallest margin, 4.2 ms, belongs to the 5 ms task. An overrun — a flag set again before it was served — needs a slot chain longer than the period of a waiting task; with normal bus behaviour that cannot happen. Both simavr runs ended with SCHED_u16GetOverruns() = 0, as did test_service over 10 s.

Fault case: stuck I²C bus (computed)

If a slave holds SDA low, every TWI wait ends after the 1.33 ms timeout, and each driver gives up after its first failed step:

  • LCD_BUF then pauses 1 s;
  • ESTORE goes to FAULT after its first failed page write;
  • LAMP and SEVEN_SEG return an error and retry at their next call.

Worst slots then become about 1.5 ms (5 ms), 2.8 ms (10 ms: lamp + EEPROM attempt), 2.9 ms (100 ms: two digits + ADC) and 2.7 ms (500 ms). In the 1001–1005 chain this can delay the 5 ms task by a few milliseconds and, in the worst case, count an overrun of the 5 ms flag (one LCD byte step lost, no wrong output). The loop never hangs. That is exactly what the timeout was added for (§2.8); test_mcal checks a timeout within 2 ms with SDA forced low.

Headroom

  • CPU: ≥ 92 % idle in every measured second.
  • Single-slot budget: the longest slot (≈ 2.1 ms) uses 21 % of its own 10 ms period, and leaves ≥ 2.8 ms before the 5 ms task that follows it.
  • RAM: ≈ 1.3 KB for the stack (§1.6).
  • Flash: 16.4 KB free.

The design could take a much higher I²C speed, more tasks or a faster terminal before timing became a constraint. The first limit would be the length of single blocking transfers, which is the place to look if features are added.
