Chapter 8Verification

In this project "verified" means: it builds with -Wall and zero warnings, the logic was traced by hand against the requirement, and a test step for it was run in Proteus (specification §2). This chapter lists the test programs, summarises the recorded Proteus runs, maps every requirement to its code and its tests, and records what failed along the way and what is still open.

8.4 Independent cross-check in simavr

The timing harness of chapter 7 doubles as a functional regression check of the binary, independent of Proteus. In the main scenario the terminal transcript produced by app.elf matches the documented protocol (uart_protocol.md) line for line, and the observed behaviour matches the requirements:

  • the 13 first-boot pages written highest first;
  • [OK] replies and [INFO] events;
  • the keypad session and its events;
  • the AC switching at the hysteresis limits;
  • heating after 10 samples;
  • the lockdown with buzzer and alert.

The scheduler counted 0 overruns in both runs. The harness, the scenarios and the analysis script are kept with the guide sources so the check can be repeated after any firmware change (Appendix H).

8.5 Design decisions and failures

The 7-segment display that failed (D-20)

The first display design used one 7447 BCD-to-7-segment decoder on PC2–PC5, two PNP digit drivers on PC6/PC7, and multiplexing from the 1 ms tick (SEVEN_SEG_voidRefresh). In Proteus it was unreliable: 37 showed as 33, and the counter showed the same odd symbol on both digits.

The test bench firmware/experiments/hal_testing_v1 isolated the cause step by step:

  • the port pins followed the code;
  • JTAG was off (MCUCSR = 128);
  • the generated code was correct (checked in the disassembly);
  • a first sampling check gave a false error because it read the digit pins and the BCD pins separately while the tick switched digits — fixed with a single port snapshot.

The real symptom was both digits conducting at once through the slow PNP drivers. A 1 ms blanking interval (SEVEN_SEG_BLANK_TICKS) did not make it reliable.

Version 1: 7447 decoder + multiplexed PNP digits (failed in Proteus). Version 2: one PCF8574 per digit (D-20, as built).

Decision D-20 (2026-10-03): two PCF8574 expanders, one per common-anode digit (tens 0x21, units 0x22). A second bench, hal_testing_v2 (bus scan, 22 raw patterns per chip, all 100 numbers, bus sharing with the LCD and lamps, stress), showed the right digits. Gains: no multiplexing, no tick hook (the Timer2 ISR does no real work at all), no JTAG handling, six port pins freed (PC2–PC7). Cost: two more I²C devices and 190 µs of bus time per changed digit.

8.6 Known limitations

  • Not built in v1 (D-16): fan speed ramp (optional part of AC-03), PIR alarm (ALM-02), LDR street light. Pins PD2 and PA2 stay reserved.
  • Security: passwords are stored and compared as plain text (D-13), and the UART link is not encrypted. Acceptable for a simulation project; hashing (and a salted record format) is the next step.
  • Timing: the blink corner case and the up-to-100 ms display/LED lag at turn-off (§7.5, §5.6).
  • Untested paths in simulation:
    • The Proteus 24C08 has no write delay, so the "chip still busy" branch of the ACK polling (NACK, retry) was never exercised. In simavr with a 5 ms model, the first poll, 10 ms after the write, always succeeded too. Only a write cycle above 10 ms, or a faulty chip, takes that branch.
    • UBRRH cannot be verified in Proteus (§2.7).
  • Robustness: no watchdog is enabled; a firmware fault that stops the loop would not be recovered. No brown-out handling is configured in firmware (the BOD fuses are a hardware setting).
  • Hardware for a real board (pin_map.md §4): NPN driver for the buzzer (C-9), series resistors on the ISP pins PB5–PB7 (C-4), a stronger base drive for the dimmer lamp transistor, AREF left open (C-5).
  • Power: the idle loop polls flags at full speed; there is no sleep mode.
