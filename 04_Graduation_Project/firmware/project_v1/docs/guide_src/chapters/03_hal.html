Chapter 3HAL — one driver per part

A HAL module hides one part, or one kind of part, behind functions that speak in the part's own terms: a lamp number, a temperature, a key, an angle. Above the HAL nobody knows a pin, an I²C address or a register. Chips that sit behind other chips form small HAL chains: LCD_BUF → CLCD → PCF8574 → TWI.

3.1 PCF8574 — I²C port expander HALF

Purpose

The PCF8574 turns one I²C byte into eight pin levels. Four of them on one bus give the LCD (0x27), the five lamps (0x20) and the two display digits (0x21, 0x22), which is how the design fits into 32 pins (§1.3).

Hardware

The address is 0100 A2 A1 A0, set by three pins. The pins are quasi-bidirectional: writing 0 turns on a strong pull-down (sinks up to 25 mA), writing 1 leaves only a weak pull-up (≈ 100 µA). So a PCF8574 drives LEDs active low, and a pin used as an input must first be written 1. At power-up all pins are 1.

Design and API

void PCF8574_voidInit();                                         /* TWI_voidMasterInit ; a second call is harmless */
u8   PCF8574_u8WritePort (u8 Address, u8 Value);                 /* START , addr+W , value , STOP */
u8   PCF8574_u8ReadPort  (u8 Address, u8 *Value);
u8   PCF8574_u8WriteBytes(u8 Address, const u8 *Data, u8 Length); /* new: several port values in ONE transaction */

Every function returns the TWI status, so the caller can see a missing chip. PCF8574_u8WriteBytes is the addition made for CLCD: the chip latches every byte as it arrives, so four bytes in one transaction produce four successive pin states, 90 µs apart.

Pitfall

Reading back a PCF8574 whose pins drive LEDs returns the pin levels, not the written latch. With segment LEDs pulling the pins, the value read in Proteus differed from the one written while the display was right. The 7-segment read-back checks were removed from test_hal (specification §4).

Re-implementation checklist

  1. Address 0x20 + A2A1A0.
  2. Write = one-byte TWI transmit.
  3. Multi-byte write for timed sequences.
  4. Return the TWI status.
  5. Drive loads active low.

3.2 CLCD — character LCD over I²C HALF

Purpose

Driver for the 16×2 HD44780-compatible LCD (LM016L), in the course's I²C mode (CLCD_MODE = CLCD_I2C_MODE). It is blocking, with about 0.46 ms per byte. Only LCD_BUF calls it after boot.

Hardware

Wiring of the LCD expander (CLCD_cfg.h, pin_map.md §2). One LCD byte becomes four port values: the high nibble with E = 1, then E = 0, then the low nibble the same way. The LCD latches data on the falling edge of E.

Design

In 4-bit mode the LCD takes every byte as two nibbles on D4–D7, each latched by a falling edge of E. The course driver sent each nibble edge as its own I²C transaction: 4 transactions × 3 bytes ≈ 1.2 ms per character. The fixed driver builds all four port values and sends them in one transaction of 5 bytes, {{ f(N['TWI_TX']['lcd_byte'],0) }} µs computed, ≈ 0.48 ms measured in Proteus (hal_summary.md). The E pulse is one I²C byte long (90 µs), far above the 450 ns the LCD needs, so no delay is added.

Init sequence (CLCD_voidInit, boot only): wait 40 ms after power-up; send nibble 0x3 three times (5 ms and 1 ms apart) to force 8-bit mode from any state; send 0x2 to switch to 4-bit mode; Function Set 0x28 (4-bit, 2 lines, 5×8); Display Control CLCD_DISPLAY_CTRL = 0x0C (display on, cursor off, blink off); Clear 0x01 followed by 2 ms (Clear and Home need 1.52 ms). Total {{ f(N['LCD_INIT_MS'],1) }} ms computed, 50.6 ms in simavr.

Cursor: CLCD_voidSetCursorPosition(x, y) sends 0x80 | (x + 0x40·y): row 0 starts at DDRAM 0x00, row 1 at 0x40.

API

void CLCD_voidInit();  void CLCD_voidSendCommand(u8);  void CLCD_voidSendData(u8);
void CLCD_voidSetCursorPosition(u8 x, u8 y);  void CLCD_voidSendString(char*);  void CLCD_voidClearDisp();
void CLCD_voidSendFlashString(const __flash c8 *);   /* new */
u8   CLCD_u8GetStatus();                             /* new: TWI status of the last write */
void CLCD_voidCreatSpecialChar(u8 Index, u8 *Pattern);

Pitfalls (fixed in Phase 2)

  • Cursor and blink were switched on at init; on a status screen that shows a blinking block. Now set from CLCD_DISPLAY_CTRL.
  • CLCD_voidClearDisp existed but was not declared in the header.
  • Writes could fail silently. CLCD_u8GetStatus() now reports the last TWI result, so LCD_BUF can retry.
  • The parallel modes (unused) still have a 10 ms enable pulse; they would block the loop if ever selected.

Re-implementation checklist

  1. Map PCF8574 bits to RS, RW, E, BL, D4–D7.
  2. Byte = 4 port values (nibble with E high, then low) in one transaction.
  3. Init: 40 ms, 0x3 ×3, 0x2, 0x28, 0x0C, 0x01 + 2 ms.
  4. Cursor = 0x80 | address (row 1 at 0x40).
  5. Keep the last TWI status.

3.3 LCD_BUF — the non-blocking LCD HALN

Purpose

Writing a 16-character line with CLCD blocks for 16 × 0.46 ms ≈ 7.5 ms, and longer with set-cursor commands. LCD_BUF keeps the loop free: writers only change RAM, and a 5 ms task copies the differences to the LCD, one byte per call (LUI-02, LUI-03).

Design

Two 32-byte arrays: Global_c8Wanted (what the application wants) and Global_c8Shown (what the LCD shows), plus the LCD's cursor position as LCD_BUF believes it to be. LCD_BUF_voidUpdate searches round-robin from the last position for a cell where the two differ. If the cursor is not on that cell, the call sends one set-cursor command. If it is, the call sends the character, marks the cell shown and advances the cursor, because the LCD auto-increments. At the end of a row the cursor is marked unknown, because the next DDRAM address (0x10) is not on screen.

The wanted/shown comparison. Only differing cells cost bus time.

Error handling: if CLCD reports an I²C error, the byte is not marked shown, the cursor becomes unknown, and the module stays quiet for LCD_BUF_RETRY_UPDATES = 200 calls = 1 s. An unplugged LCD therefore costs one failed transaction per second, not one per 5 ms.

Timing (computed)

One character changed (cursor elsewhere)2 calls → visible after 5–10 ms
Full screen redraw (32 cells + 2 cursor moves)34 calls × 5 ms = 170 ms
Longest callone transaction, {{ f(N['TWI_TX']['lcd_byte'],0) }} µs computed · 0.49 ms Proteus (hal_summary.md)
Proteus I²C debugger (presentation capture): one LCD transaction S 4E xx xx xx xx P every 5 ms (452.122 s, 452.127 s, …) — the LCD_BUF cadence.

API

void LCD_BUF_voidInit();     /* CLCD_voidInit (blocking , boot) + both buffers blank */
void LCD_BUF_voidClear();    /* RAM only */
void LCD_BUF_voidWriteChar (u8 Row, u8 Col, c8 Char);
void LCD_BUF_voidWriteFlash(u8 Row, u8 Col, const __flash c8 *Text);   /* cut at the row end */
void LCD_BUF_voidWriteRam  (u8 Row, u8 Col, const c8 *Text);
void LCD_BUF_voidUpdate();   /* every 5 ms : at most ONE byte to the LCD */

Re-implementation checklist

  1. Two cell arrays, wanted and shown.
  2. Writers touch only wanted.
  3. Update: find the next difference; set the cursor or send one char.
  4. Track the auto-incremented cursor; forget it at row ends and on errors.
  5. Back off after an error.

3.4 KPAD — 4×4 keypad HALF

Purpose

Reads the calculator keypad (7 8 9 / · 4 5 6 * · 1 2 3 - · C 0 = +) for UILOC (LUI-02). It adds a non-blocking, debounced scan next to the course's blocking function.

Keypad matrix and scan (KPAD_cfg.h, KPAD_MAT).

Design

KPAD_voidUpdate runs every 10 ms. It drives each column low in turn, waits 5 µs for the row lines to settle through the pull-ups, reads the four rows, and drives the column high again; the first low row gives the key. A key becomes the stable value after KPAD_DEBOUNCE_SCANS = 2 equal scans. A new stable key is stored once in Global_u8Pending; KPAD_u8GetKey() returns it once and then KPAD_NO_KEY (0xFF), so a held key gives exactly one event. The key table and the pin arrays are static const __flash: plain const data is still copied to RAM on the AVR, and __flash keeps the 24 bytes in program memory.

Timing

A clean press is accepted on the 2nd scan that sees it, 10–20 ms after the contact closes (computed). UILOC reads the key in the same 10 ms slot, right after KPAD_voidUpdate. simavr measured {{ f(R['latency']['key_lamp']['lamp_write_after_ms'],1) }} ms from key-down to the lamp write.

Pitfalls (fixed)

  • The course table was transposed (row/column swapped), and one column was left low after a key was found (Phase 0).
  • KPAD_u8GetKeyPressed waits until the key is released, which blocks the loop for as long as the key is held. It is kept only for test_base.

Re-implementation checklist

  1. Rows = inputs with pull-ups, columns = outputs, idle high.
  2. Scan: column low, short settle, read rows, column high.
  3. Debounce: N equal scans.
  4. Report a new key once.
  5. Keep the tables in flash.

3.5 BUTTON — heater push buttons HALN

Purpose

Debounced level and press/release events for ON/OFF (PD6), Up (PD7) and Down (PB5) (HTR-01, HTR-02, HTR-05).

Each button connects its pin to ground; the internal pull-up holds the pin high when released.

Design

Every 10 ms BUTTON_voidUpdate reads the three pins. If a pin differs from the debounced level, a counter runs; after BUTTON_DEBOUNCE_SAMPLES = 3 differing samples in a row the level changes and a press or release flag is set. A sample equal to the old level restarts the count, so a bounce is ignored. The event flags are cleared by reading them.

Debounce timing. BUTTON debounce as a state machine (per button).

HEATER acts on the release of ON/OFF (HTR-05), so holding the button does nothing, and on the press of Up and Down.

API

void BUTTON_voidInit();  void BUTTON_voidUpdate();          /* every 10 ms */
u8 BUTTON_u8IsPressed(u8 ID);  u8 BUTTON_u8GetPressEvent(u8 ID);  u8 BUTTON_u8GetReleaseEvent(u8 ID);
/* IDs: BUTTON_ONOFF 0 , BUTTON_UP 1 , BUTTON_DOWN 2 */

Re-implementation checklist

  1. Inputs with pull-ups; pressed = low.
  2. Count consecutive differing samples.
  3. Change the level after N samples and raise an event.
  4. Reset the count on a bounce.
  5. Clear events on read.

3.6 LM35 — temperature sensors HALN

Purpose

Two LM35s: ambient air for the AC (PA0, AC-01) and water for the heater (PA1, HTR-07).

LM35 wiring. ADC value against temperature. The thresholds used by CLIMATE and HEATER are marked.

Design

With the 2.56 V reference, one ADC step is 2.5 mV = 0.25 °C, so the raw ADC value is the temperature in quarter degrees. LM35_u16ReadTempX4 returns it unchanged; CLIMATE and HEATER keep everything in this unit and round to whole degrees only for display: (x4 + 2) / 4. An unknown sensor ID returns 0. The range ends at 1023 / 4 = 255.75 °C, well above the 0–100 °C an LM35 delivers here.

Re-implementation checklist

  1. Pick Vref so that 1 LSB is a round fraction of a degree.
  2. Return raw counts.
  3. Compare thresholds in counts (× 4).
  4. Round only for display.
  5. Leave AREF open with the internal reference.

3.7 SEVEN_SEG — two-digit display HALN

Purpose

The heater's display: water temperature, or the blinking set temperature (HTR-10, HTR-11). Each common-anode digit has its own PCF8574 (tens 0x21, units 0x22), with no multiplexing (D-20). The history of this design is in §8.5.

One digit: common anode on +5 V; each segment is lit when its PCF8574 pin is low. Segment patterns of SEVEN_SEG_TABLE.

Design

The module remembers what each chip shows (Shown) and whether that is known (Known). SetNumber, Enable and Disable compute both patterns and write a chip only if its pattern differs from what it shows. Changing 55 to 56 costs one 190 µs write, not two; repeating a number costs nothing. A failed write marks that digit unknown, so the next call writes it again. Numbers above 99 show 99; a number below 10 shows a leading zero.

API

void SEVEN_SEG_voidInit();                  /* blank */
void SEVEN_SEG_voidSetNumber(u8 Number);    /* 0..99 */
void SEVEN_SEG_voidEnable();  void SEVEN_SEG_voidDisable();   /* show / blank (0xFF on both chips) */
u8   SEVEN_SEG_u8GetStatus();               /* TWI status of the last write */

Re-implementation checklist

  1. Pattern table, a 0 bit = lit (common anode).
  2. One expander per digit: no refresh needed.
  3. Write only changed digits.
  4. Mark a digit unknown after a failed write.
  5. Call from the main loop only (the bus is polled).

3.8 LAMP — five lamps on a PCF8574 HALN

Purpose

On/off control of lamps 1–5 on P0–P4 of the expander at 0x20 (LGT-01).

One lamp channel (Proteus uses an LED per lamp).

Design

The PCF8574 cannot be read back reliably as an output latch, so LAMP keeps a RAM copy of the port, Global_u8Port, starting at 0xFF (all off, unused pins high). To switch a lamp it changes one bit in a copy of that byte, writes the whole byte, and stores it as the new state only if the chip acknowledged. After an I²C error the copy still matches the chip. The level for "on" comes from LAMP_ON_LEVEL = 0.

API

void LAMP_voidInit();                         /* all off */
u8   LAMP_u8SetState(u8 Lamp, u8 State);      /* lamp 1..5 , LAMP_ON / LAMP_OFF ; TWI status or LAMP_ERR_NUMBER (0xFF) */
u8   LAMP_u8GetState(u8 Lamp);                /* last state written successfully */

Re-implementation checklist

  1. Shadow byte of the port.
  2. Change a bit in a copy, write the byte.
  3. Commit the copy only on ACK.
  4. Active-low level as a cfg constant.
  5. Distinct error code for a bad lamp number.

3.9 RELAY, LED, BUZZER — plain outputs HALN

Three small drivers with the same shape: an ID, _voidOn, _voidOff, and an init that sets the off level before making the pin an output, so nothing switches on during reset. RELAY has RELAY_HEATING (PB6) and RELAY_COOLING (PB7); LED has LED_HEATER (PA3); BUZZER is PD3. All are active high.

Heater outputs in Proteus: LEDs stand for the solid-state relays. Buzzer: direct in Proteus; the driver stage a real board needs.

HEATER guarantees that the two elements are never on together: it always switches one off before switching the other on (§5.6).

3.10 DIMMER, SERVO, FAN — PWM outputs HALN

Three drivers on the PWM channels of chapter 2. They share the same corner-case rules: 0 % = compare output disconnected and the pin driven low (a compare value of 0 still gives a one-count spike), 100 % = compare value equal to TOP (constant high), and values above the range are clamped.

Dimmer: PWM → RC filter → transistor → 12 V lamp. AC fan: OC1B → 1 kΩ → NPN; flyback diode across the motor.
Door servo: the signal pin takes the 1–2 ms pulse directly.

Pitfall

The dimmer lamp stage: with R6 = 10 kΩ the base current is at most (5 − 0.7) V / 10 kΩ = 0.43 mA, while a 12 V / 24 Ω lamp needs 0.5 A. Unless the transistor gain is above about 1000, the lamp stays dim even at 100 %. pin_map.md notes the remedies (R6 = 1 kΩ, or a lighter lamp load in Proteus); no firmware change is involved.

3.11 EXT_EEPROM — the 24C08 HALN

Purpose

Raw access to the 1 KB I²C EEPROM that holds the accounts and the heater set temperature (EEP-01). It knows the chip's two quirks, blocks and pages; the RAM image and the write-behind logic are one layer up in ESTORE.

24C08 wiring: A2 and WP to ground.

Hardware

  • Blocks: 1024 bytes need 10 address bits, but one word-address byte carries 8. Bits 9:8 (B1 B0) travel in the slave address: block 0 = 0x50 … block 3 = 0x53. A read is split at 256-byte borders. The project uses block 0 only (bytes 0x00–0xCF).
  • Pages: a write may carry 1–16 bytes, all inside one 16-byte page; past the page end the chip wraps to the page start. EXT_EEPROM_u8WritePage refuses anything that would cross a page.
  • Write cycle: after the STOP the chip programs the page for up to 5 ms and does not acknowledge its address meanwhile. That NACK is the "ready" signal: ACK polling.
How ESTORE uses the three functions: a page write in one 10 ms slot, one ACK poll in the next.

API

void EXT_EEPROM_voidInit();
u8   EXT_EEPROM_u8ReadBlock(u16 Address, u8 *Data, u8 Length);       /* blocking , ≈ 90 µs per byte : boot only */
u8   EXT_EEPROM_u8WritePage(u16 Address, const u8 *Data, u8 Length); /* 1..16 bytes in ONE page ; returns after the STOP */
u8   EXT_EEPROM_u8IsReady();                                         /* ONE probe : 1 = write cycle over ; never waits */

Timing (computed)

Page write = START + address + word address + 16 data = 18 bytes → {{ f(N['TWI_TX']['ee_page'],0) }} µs. ACK poll = START + address + STOP → {{ f(N['TWI_TX']['ee_poll'],0) }} µs. Boot read of 208 bytes = write phase (2 bytes) + repeated START + read phase (209 bytes) → {{ f(N['TWI_TX']['ee_boot_read']/1000,2) }} ms (simavr: 19.3 ms).

Pitfall

The Proteus 24C08 model has no write-cycle delay: it acknowledges right after a write, so the first poll always succeeds. Real chips need the polling, so it is written for them (specification §4). pin_map.md §2 still says the model has TD_WRITE = 10 ms; that contradicts the other documents and the observed behaviour.

Re-implementation checklist

  1. Slave address = 0x50 | address bits 9:8.
  2. Read: write the word address, repeated START, read with ACK … NACK.
  3. Write: one page at most, never across a border.
  4. Ready = one probe; never loop on it.
  5. Leave timing decisions to the caller.
